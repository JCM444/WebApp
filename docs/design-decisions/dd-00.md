# 00: Wie verifizieren wir die Hochschulzugehörigkeit?

| Property | Value |
|--:|:--|
| **Status** | 🟡 Work in progress |
| **Updated** | 15.11.2026 |
| **Lead** | Ahmed Bauer |

## Problem Statement

Study Circle ermöglicht Studierenden der HWR Berlin, gemeinsame Lernsessions zu erstellen und daran teilzunehmen. Um Fake-Accounts zu reduzieren und eine vertrauenswürdige Lerncommunity zu schaffen, soll die Zugehörigkeit zur HWR Berlin bei der Registrierung überprüft werden.

**Die Anforderungen lauten demnach:**
- Login über eine echte Hochschulidentität, möglichst einfach
- Keine Speicherung / Verwaltung von Benutzerpasswörtern
- Umsetzung in Flask/Python
- Kostenfreie Nutzung

**Zu entscheiden:** Wie lässt sich die Hochschulzugehörigkeit zuverlässig und mit vertretbarem Aufwand umsetzen?
## Decision

Aktuell bevorzugt: [Studid](https://studid.io/guide). Studid authentifiziert kostenlos über das bestehende Hochschul-SSO (SAML), ohne dass eine eigene Anbindung an den [HWR-Shibboleth-Dienst](https://it.hwr-berlin.de/servicekatalog/verzeichnisdienste/shibboleth/) beantragt werden muss. Die Integration erfolgt über eine frei zugängliche REST-API.

## Regarded options

### Option 1: Studid

**Vorteile:** Verifizierung über Hochschulidentität; REST-API für Flask; keine eigene SAML-Implementierung.

**Nachteile:** Abhängigkeit von einem externen Anbieter (Verfügbarkeit noch zu prüfen); Callback-Integration nötig; Hochschule gibt keine `affiliations` frei

### Option 2: E-Mail-Verifikation

Nutzer registrieren sich mit ihrer Hochschul-E-Mail-Adresse und bestätigen diese über einen Verifizierungslink.

**Vorteile:** Unabhängige Umsetzung von einem Hochschul-SSO; volle Kontrolle über den Registrierungsprozess

**Nachteile:** Eigene Implementierung und Absicherung der E-Mail-Verifikation sowie des anschließenden Loginverfahrens erforderlich.

### Option 3: Direkte SAML-Integration

StudyCircle wird direkt an den Identity Provider der Hochschule angebunden.

**Vorteile:** Direkte Authentifizierung über die Hochschule; Keine Abhängigkeit von einem zusätzlichen Vermittlungsdienst wie Studid.

**Nachteile:** Hoher Integrations- und Wartungsaufwand; Komplexere Sicherheitsanforderungen; Technische und organisatorische Freigabe durch die Hochschule ggf. notwendig

## Tests: Studid REST API

### Endpunkte

| Methode | Endpoint | Zweck |
|---|---|---|
| `POST` | `https://api.studid.io/v2/auth/verification` | Verifizierung anlegen; Antwort `201` mit `id` und `link` (SSO-Weiterleitung) |
| `GET` | `https://api.studid.io/v2/auth/verification/{id}` | Ergebnis und Hochschulidentität abrufen |

### Authentifizierung

Keine Registrierung und kein API-Key nötig. Stattdessen erzeugt die Anwendung pro Verifizierung ein eigenes `secretToken`.

### Beispiel-Response (`GET /v2/auth/verification/{id}`)

```json
{
  "id": "<verification-uuid>",
  "created": "2026-11-15T20:52:03.425Z",
  "session": {
    "entityId": "https://identity.hwr-berlin.de/idp/shibboleth",
    "affiliations": [],
    "authIdentifier": "<id>@hwr-berlin.de",
    "authIdentifierType": "pairwise-id",
    "test": false
  }
}
```

**Ergebnis:** Der erste Test mit dem HWR-SSO war erfolgreich. Studid lieferte die HWR als Identity Provider sowie einen pseudonymen Benutzer-Identifier vom Typ `pairwise-id`. Dieser ist grundsätzlich für die Wiedererkennung geeignet. Die `affiliations` waren leer. Dazu heißt es in der Spezifikation: „Empty when the institution does not release affiliation attributes; the authentication is still valid.“ (Studid o. J., Schema `Session`, Feld `affiliations`) Damit ist die Zugehörigkeit zur HWR belegt, ein Studierendenstatus (im Unterschied zu Mitarbeitenden) lässt sich aber nicht feststellen.
